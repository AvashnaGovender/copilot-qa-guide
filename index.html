Test Case Creation & Improvement

Using Copilot to generate test cases from requirements and catch the edge cases humans miss.

💡
What this means in plain terms

A test case is essentially a script that says: "Given this starting condition, when I do X, I expect Y to happen." Writing them manually is slow and humans consistently miss edge cases — the weird inputs, the empty fields, the boundary values.

With Copilot, you paste in a requirement or user story and ask it to generate a full set of test cases — including the happy path (everything works), negative paths (what breaks), and boundary conditions (e.g. max characters, zero values, nulls).

Think of Copilot as a junior QA analyst who has read every testing textbook — it knows all the patterns, it just needs you to give it the context.

⚡

Review these existing test cases: [paste test cases] — identify gaps in coverage, missing edge cases, and any redundant tests. Suggest improvements. click to copy
For a login feature that accepts email and password, generate test cases specifically for: invalid inputs, SQL injection attempts, max-length fields, special characters, and session handling. click to copy
Copilot Chat Inline suggestions Works in VS Code & GitHub
🎯
Pro tip

The more context you give, the better. Don't just say "test the login page" — paste the actual acceptance criteria or user story. Copilot uses that to generate relevant, specific test cases rather than generic ones.

Use #file in Copilot Chat to reference your actual source code or spec files directly: Generate test cases for #file:auth.service.ts

Test Prioritisation (Risk-Based Testing)

Using AI to decide which tests to run first when you can't run everything.

💡
What this means in plain terms

Imagine you have 500 test cases but only 2 hours before a release. Which 50 do you run? That's test prioritisation. Traditionally, teams make this call based on gut feel or experience.

Risk-based testing means you analyse: which parts of the code changed, which areas historically had the most bugs, and which features have the highest business impact — then run those tests first.

Copilot can help by analysing a code diff (what changed between versions), your defect history, and your test suite to recommend an execution order.

⚡
Copilot Prompts — click to copy
Here is a git diff of recent code changes: [paste diff]. Based on the changed files and functions, which areas of the application carry the highest risk and should be tested first? List them in priority order with reasoning. click to copy
Here is our defect history from the past 3 sprints: [paste bug list with module names]. Identify which modules have the highest defect density and suggest which test cases to prioritise in our next regression run. click to copy
Given these test cases [paste list] and this sprint's changes touching [module A, module B] — suggest a prioritised smoke test suite of no more than 20 test cases that covers the highest risk areas. click to copy
Copilot Chat Pair with git history
🎯
Pro tip

Use git diff main..feature-branch --stat to get a summary of changed files and paste that into Copilot Chat. This gives it real signal about what actually changed — not assumptions.

Over time, consider maintaining a simple CSV of defects with module names. That becomes powerful input for Copilot to identify patterns.

Automated Test Script Generation

Getting Copilot to write Playwright + TypeScript test scripts so your team spends less time scripting and more time testing.

💡
What this means in plain terms

Playwright is a tool that controls a real browser automatically — it clicks buttons, fills forms, navigates pages, and checks that things work, all in code. Writing these scripts by hand is tedious and repetitive.

Copilot is exceptionally good at this because Playwright scripts follow very consistent patterns. You describe what the test should do in plain English, and Copilot generates the TypeScript code. Think of it like pair programming where your pair has memorised the entire Playwright API.

The biggest win: Copilot understands your existing code via #file context, so it generates scripts that match your project's structure and conventions — not generic examples.

⚡
Copilot Prompts — click to copy
Write a Playwright TypeScript test for the following scenario: A user navigates to /login, enters email "test@example.com" and password "Test@1234", clicks the login button, and is redirected to /dashboard. Assert the dashboard header is visible. click to copy
Here is an existing Playwright test file: #file:login.spec.ts — generate 5 additional test cases following the same style and patterns, covering: invalid credentials, empty fields, password reset link, and session expiry. click to copy
Convert this manual test case into a Playwright TypeScript test: [paste test case steps]. Use the Page Object Model pattern. Include proper assertions and error messages. click to copy
Generate a Playwright test that tests a form with these fields: [list fields]. Include validation testing for each field, and ensure data-testid selectors are used throughout. click to copy
Copilot Chat Inline autocomplete Use #file for context
🎯
Pro tip

Start comments with // Test: in your .spec.ts files and Copilot's inline autocomplete will often complete the entire test block for you — no chat needed.

Ask Copilot to generate a Page Object Model class for pages you test frequently. This means your test scripts stay clean and reusable — a standard industry practice Copilot handles well.

Bug Detection & Debugging Assistance

Using Copilot to analyse logs, interpret error messages, and identify root causes faster.

💡
What this means in plain terms

When a test fails or production breaks, you get logs and error messages — walls of text that tell you what happened but not necessarily why. A junior dev might spend hours parsing these. Copilot can read them in seconds.

You paste in a stack trace, error log, or failing test output, and ask Copilot to explain what's wrong, why it happened, and what to try. It's particularly good at pattern recognition — if the same class of bug has appeared before in your codebase (which you can show it via #file), it will reference it.

This is one of the highest-ROI uses of Copilot for QA teams — it dramatically reduces the time between "a test failed" and "we know what to fix."

⚡
Copilot Prompts — click to copy
Here is a stack trace from a failed test: [paste stack trace]. Explain what went wrong in plain language, identify the likely root cause, and suggest 3 possible fixes. click to copy
Analyse this application error log: [paste log snippet]. Identify any patterns, recurring errors, or warning signs of underlying issues. Group errors by type and suggest investigation priorities. click to copy
This Playwright test is failing intermittently (flaky): [paste test code]. What are the most likely causes of flakiness in this test, and how would you make it more stable? click to copy
Given this function #file:payment.service.ts and this error message "[paste error]" — walk me through how to debug this step by step, including what to log and where to add breakpoints. click to copy
Copilot Chat Paste logs directly #file for source context
🎯
Pro tip

When pasting logs, trim them to the relevant section — Copilot works with context windows, and a 10,000-line log will dilute the signal. The key portion is usually the first error and the stack trace directly beneath it.

Ask Copilot to suggest what additional logging you should add to make future debugging easier — this is a great way to improve your codebase incrementally.

Regression Testing Optimisation

Reducing the regression suite to only the tests that matter for each release.

💡
What this means in plain terms

Regression testing means re-running tests every time code changes to make sure nothing that worked before is now broken. The problem: as a product matures, the regression suite grows to hundreds or thousands of tests — running all of them for every small change is wasteful and slow.

The goal is to select the minimum effective set — tests that cover what actually changed, without running tests that have nothing to do with the change. AI helps by understanding which code changed, which tests cover that code, and which other tests are functionally duplicated.

Think of it like: if only the checkout page changed, you probably don't need to re-run tests for the user profile page. But you do need to run payment, cart, and session tests.

⚡
Copilot Prompts — click to copy
Here are the files changed in this sprint: [list files/modules]. Here is our full test suite list: [paste test names]. Identify which tests are relevant to the changed code and produce an optimised regression suite. click to copy
Review this list of test cases: [paste list]. Identify any tests that appear to cover overlapping functionality and suggest which can be consolidated or removed without reducing meaningful coverage. click to copy
Given #file:checkout.service.ts was modified — list all the areas of functionality that could potentially be affected by changes in this file and should be regression tested. click to copy
Copilot Chat Combine with code diff
🎯
Pro tip

Tag your test cases with feature area labels (e.g. @checkout, @auth, @profile). This makes it far easier to ask Copilot — or run programmatically — only the tests relevant to what changed.

In Playwright, this is done with test.describe groups and the --grep flag. Copilot can help you retrofit tags onto an existing suite: "Add describe blocks and tags to this test file following [convention]."

Self-Healing Automation

Keeping automation scripts alive when the UI changes without manual re-scripting.

💡
What this means in plain terms

Automation scripts find UI elements by locators — things like an element's ID, class name, or position on the page. When a developer changes a button's ID from btn-submit to submit-btn, your automation script breaks — even though the app itself is fine.

This is one of the biggest maintenance headaches in QA automation. Self-healing means the script (or a tool) detects that the locator no longer works and automatically finds a new one.

Copilot can help here in two ways: (1) it can suggest more resilient locators upfront (using text content or ARIA roles rather than fragile CSS classes), and (2) when scripts break, it can quickly generate updated locators given the new HTML.

⚡
Copilot Prompts — click to copy
Here is the old HTML for a button: [paste old HTML]. Here is the new HTML after a UI update: [paste new HTML]. Update the Playwright locator in this test to work with the new structure: [paste test code]. click to copy
Review these Playwright locators: [paste locators]. Identify any that are fragile (relying on auto-generated IDs, index positions, or unstable class names) and suggest more resilient alternatives using ARIA roles, data-testid, or visible text. click to copy
Our UI uses a component library and element IDs change frequently. Write a Playwright helper utility that tries multiple selector strategies in order of reliability: data-testid → aria-label → role → text → CSS fallback. click to copy
Copilot Chat Pair with: Healenium Pair with: Testim.io
🎯
Pro tip — purpose-built self-healing tools

Healenium (open source, free) is a library that wraps Selenium/Playwright and automatically tries to find a new locator when one breaks — using a tree-comparison algorithm. It works well for teams already using those frameworks.

Testim, Mabl, and Reflect are commercial AI-driven testing platforms with built-in self-healing. They're worth evaluating if your team's scripts break frequently due to rapid UI changes.

The preventative approach (use data-testid attributes on all interactive elements from the start) is the most reliable long-term strategy — Copilot can help enforce this in code reviews.

API Testing Support

Generating Postman collections, schema validation, and comprehensive API test coverage with Copilot.

💡
What this means in plain terms

An API is the layer of the application that your frontend talks to — it handles requests like "get me the user's orders" or "process this payment." Testing APIs means calling those endpoints directly and checking that they return the right data, the right status codes, and handle bad input correctly.

Postman is a tool for sending API requests and organising them into collections. A schema defines the structure of an API response — validation means confirming the response matches what's expected.

Copilot can generate an entire Postman collection from an OpenAPI spec, write API tests in code (e.g. using Playwright's API testing or Supertest), and identify status codes your team hasn't tested (like 401, 403, 429, 503).

⚡

Write a Playwright API test in TypeScript for this endpoint: [describe endpoint]. Include: happy path, validation errors (400), auth failure (401), not found (404), and assert the response schema matches this structure: [paste expected JSON shape]. click to copy
Review these API test cases: [paste list]. What status code scenarios are missing? What security-related tests (auth bypass, injection, mass assignment) should be added? click to copy

Pro tip

If your team uses Swagger / OpenAPI specs, paste the YAML or JSON directly into Copilot Chat — it can generate a full test suite from it in one shot, covering every endpoint and method defined.

Copilot also integrates with Postman's AI features (Postbot) for in-Postman test generation — worth enabling if your team uses Postman as a primary tool.

Performance & Load Testing Assistance

Generating JMeter scripts, interpreting results, and pinpointing bottlenecks with AI.

💡
What this means in plain terms

Load testing means simulating many users hitting your application at the same time to see if it holds up. A single user experience might be fine, but what happens when 500 users try to log in simultaneously?

JMeter is an open-source tool that simulates this traffic. Writing JMeter test plans (called thread groups, samplers, and listeners) is technically involved — this is where Copilot helps significantly.

Beyond writing scripts, Copilot can also help you interpret performance results — things like response time percentiles, throughput, error rates — and identify where bottlenecks are likely occurring (database queries, slow endpoints, memory issues).

⚡
Copilot Prompts — click to copy
Generate a JMeter test plan in JMX format to load test our login endpoint at POST /api/auth/login. Simulate 200 concurrent users, ramp up over 60 seconds, run for 5 minutes, and include assertions for response time under 2 seconds and status 200. click to copy
Here are JMeter performance test results: [paste summary — avg response time, error %, throughput, 90th/95th percentile]. Interpret these results, flag any concerning metrics, and suggest what to investigate as potential bottlenecks. click to copy
Our API is showing high response times under load. Here is the endpoint code: #file:orders.controller.ts. What performance issues can you identify in this code, and what optimisations would you recommend? click to copy
Copilot Chat Pair with: JMeter Also: k6, Artillery
🎯
Pro tip — modern alternatives to JMeter

k6 (by Grafana) is a modern load testing tool that uses JavaScript — meaning Copilot can write k6 scripts even more fluently than JMeter XML. If the team hasn't committed to JMeter yet, k6 is worth evaluating: k6 run script.js is much simpler to use and integrates well with CI/CD.

Artillery is another JS/YAML-based alternative that's lighter weight and CI-friendly. Ask Copilot: "Write an Artillery load test for our checkout API that tests 100 users/minute for 3 minutes."

Documentation & Reporting

Using Copilot to produce test plans, defect reports, release notes, and summaries faster.

💡
What this means in plain terms

QA teams produce a lot of written output: test plans (what will be tested, when, and by whom), defect reports (formal bug write-ups), test summaries (what was tested and what the results were), and release notes (what changed in this version).

These documents are important but time-consuming to write well. Copilot can generate first drafts from structured input — you provide the raw facts, it formats them into professional documentation.

It's also excellent at standardising defect reports — a common QA problem is inconsistent bug write-ups that developers find hard to action. Copilot can enforce a template every time.
