01

Test Case Creation & Improvement

Using Copilot to generate test cases from requirements and catch the edge cases humans miss.

💡
What this means in plain terms

A test case says: "Given this starting condition, when I do X, I expect Y to happen." Writing them manually is slow and humans miss edge cases — weird inputs, empty fields, boundary values.

With Copilot, you paste in a requirement and ask it to generate a full set — happy path (everything works), negative paths (what breaks), and boundary conditions. Think of it as a junior QA analyst who has read every testing textbook.

🚶

Test Prioritisation (Risk-Based Testing)

Using AI to decide which tests to run first when you can't run everything.

💡
What this means in plain terms

You have 500 test cases but only 2 hours before a release. Which 50 do you run? Risk-based testing analyses: which code changed, which areas had the most bugs, which features have the highest business impact — then runs those first.

Copilot can analyse a code diff, your defect history, and your test suite to recommend a prioritised execution order in minutes.

Regression Testing Optimisation

Reducing the regression suite to only the tests that matter for each release.

💡
What this means in plain terms

Regression testing re-runs tests every time code changes to confirm nothing that worked before is now broken. As a product grows, the suite can reach thousands of tests — running all of them for every small change is wasteful and slow.

AI helps identify which tests are relevant to what actually changed, and which tests are duplicates. If only the checkout page changed, you don't need to re-run tests for the user profile page.

🚶

Tests in modules unchanged for 6+ months (candidates for monthly-only regression) 3. Any tests with descriptions so broad they likely overlap with others Goal: reduce to a 90-minute sprint suite without losing meaningful coverage.click to copy
Copilot output (excerpt)

Self-Healing Automation

Keeping automation scripts alive when the UI changes without manual re-scripting.

💡
What this means in plain terms

Automation scripts find UI elements by locators — an element's ID, class name, or position. When a developer renames a button's ID, your script breaks — even though the app is fine. This is one of the biggest maintenance headaches in QA automation.

Copilot helps in two ways: suggesting resilient locators upfront (ARIA roles, data-testid), and quickly regenerating broken locators when given the new HTML.

🚶
Real-world walkthrough
Scenario: The frontend team migrated from a custom CSS library to Tailwind. Overnight, 34 automation tests broke because all the CSS class-based locators changed. QA engineer Thabo needs to fix them fast.
1
Thabo copies the old and new HTML from Chrome DevTools
Old HTML (before Tailwind)

New HTML (after Tailwind)
<button class="bg-blue-600 hover:bg-blue-700 text-white font-bold py-2 px-4 rounded" type="submit" aria-label="Complete registration">Register</button>
↓ He pastes both into Copilot Chat with his test file
2
He asks Copilot to fix and future-proof the locators
Our UI migrated to Tailwind and these locators are all broken. Here is the old and new HTML for our registration form: [paste both]. Here is the test file: #file:tests/registration.spec.ts Update all locators to work with the new HTML. Performance & Load Testing Assistance

Generating load testing scripts, interpreting results, and pinpointing bottlenecks with AI.

💡
What this means in plain terms

Load testing simulates many users hitting your application simultaneously. A single-user experience might be fine — but what happens when 500 suppliers submit documents at once?
